Asosiy REST API Mavzu #1

REST API Nima? Dasturlararo Muloqot Ko'prigi

REST (Representational State Transfer) — zamonaviy veb va mobil ilovalar, mikroservislar hamda tashqi tizimlar o'rtasida ma'lumot almashish uchun eng keng tarqalgan me'moriy uslubdir (Architectural Style). U HTTP protokoli imkoniyatlaridan to'liq foydalangan holda mijoz (Frontend) va server (Backend) ning bir-biridan mutlaqo mustaqil ishlashini ta'minlaydi.

  • Platformadan mustaqil: Backend Python, Java yoki Node.js da yozilgan bo'lsa ham, Frontend (React, iOS, Android) unga bir xil JSON orqali so'rov yubora oladi.
  • Stateless (Holatsiz): Har bir so'rov o'z ichida serverga uni tushunish uchun kerak bo'lgan barcha ma'lumotlarni (token, parametrlar) olib kelishi shart.
  • Resurslarga asoslangan (Resource-based): Hamma narsa (foydalanuvchilar, mahsulotlar, buyurtmalar) URL orqali murojaat qilinuvchi resurs hisoblanadi.
HTTP / REST Client 
# Foydalanuvchilar ro'yxatini olish uchun REST so'rovi
GET /api/v1/users HTTP/1.1
Host: api.w3learn.uz
Accept: application/json
🌐 REST API HTTP Response:
💡 REST — qat'iy standart yoki protokol emas, balki Roy Fielding tomonidan 2000-yilda taklif qilingan tavsiyaviy me'moriy qoidalar to'plamidir.

Protokol REST API Mavzu #2

HTTP Protokoli Asoslari (Client-Server)

REST API butunlay HTTP (HyperText Transfer Protocol) ustida qurilgan. Muloqot har doim Mijozning so'rovi (Request) va Serverning javobidan (Response) iborat bo'ladi.

  • Request: Metod (GET, POST), URL manzil, Sarlavhalar (Headers) va Tana (Body).
  • Response: Status kodi (200, 404), Sarlavhalar va Qaytgan ma'lumot (Body).
  • Stateless tabiati tufayli server har bir so'rovni avvalgilaridan mustaqil, yangi so'rov deb qabul qiladi.
HTTP / REST Client 
# HTTP So'rov va Javob anatomiyasi
curl -i https://jsonplaceholder.typicode.com/posts/1
🌐 REST API HTTP Response:
💡 Zamonaviy internetda ma'lumotlar o'g'irlanishining oldini olish uchun faqat shifrlangan HTTPS (port 443) ishlatiladi.

Dizayn REST API Mavzu #3

URL va URI Strukturasi (Endpoints)

REST da har bir resurs o'zining tushunarli va mantiqiy URL manziliga (Endpoint) ega bo'lishi kerak. REST qoidalariga ko'ra, URL manzillarda fe'llar (verbs) emas, balki otlar (nouns) va ko'plik shakli (plural) ishlatiladi.

  • To'g'ri (RESTful): GET /api/v1/products (barcha mahsulotlar).
  • To'g'ri (Aniq ID): GET /api/v1/products/42 (42-ID li mahsulot).
  • To'g'ri (Bog'langan resurs): GET /api/v1/users/5/orders (5-foydalanuvchining buyurtmalari).
  • ❌ Noto'g'ri: GET /api/v1/getAllProducts yoki POST /api/v1/deleteUser (harakatlar URL da emas, HTTP metodlarida ifodalanadi!).
HTTP / REST Client 
# RESTful URL namunalari:
GET    /api/v1/courses          # Kurslar ro'yxati
POST   /api/v1/courses          # Yangi kurs qo'shish
GET    /api/v1/courses/10       # 10-kursni ko'rish
PUT    /api/v1/courses/10       # 10-kursni yangilash
DELETE /api/v1/courses/10       # 10-kursni o'chirish
🌐 REST API HTTP Response:
💡 Harakat nima ekanligini URL emas, HTTP metodi (GET, POST, PUT, DELETE) belgilaydi.

Format REST API Mavzu #4

JSON Formati: Standart Ma'lumot Tili

JSON (JavaScript Object Notation) — inson o'qishi uchun ham, kompyuter tahlil qilishi uchun ham o'ta yengil va qulay universal matnli ma'lumot almashish formati.

  • Maydon nomlari (keys) har doim qo'shtirnoq "..." ichida bo'lishi shart.
  • Qo'llab-quvvatlanuvchi turlar: String, Number, Boolean (true/false), Array [], Object {}, null.
  • XML ga nisbatan hajmi 50% ga ixcham va brauzerlarda juda tez tahlil qilinadi (parse).
HTTP / REST Client 
// JSON obyekti namunasi
{
  "kursId": 101,
  "nomi": "REST API Chuqurlashtirilgan",
  "narxi": 0,
  "faolmi": true,
  "muallif": {
    "ism": "Avazbek",
    "email": "avazbek@w3learn.uz"
  },
  "mavzular": ["HTTP", "Metodlar", "Status kodlar", "Xavfsizlik"]
}
🌐 REST API HTTP Response:
💡 JSON da eng oxirgi elementdan keyin vergul qoldirish (trailing comma) sintaktik xato hisoblanadi.

Metodlar REST API Mavzu #5

GET Metodi: Ma'lumotlarni Xavfsiz O'qish

Serverdan resurslarni yuklab olish uchun ishlatiladi. GET so'rovi xavfsiz (safe) va idempotent bo'lishi shart — ya'ni u serverdagi ma'lumotlarni o'zgartirmasligi lozim.

  • So'rov tanasi (body) bo'lmaydi; parametrlar URL ning o'zida (query params) uzatiladi.
  • Brauzerlar va oraliq proksi serverlar tomonidan keshlanadi (Cached).
  • Idempotent: Bitta GET so'rovini 1 marta yoki 1000 marta yuborsangiz ham natija va server holati bir xil qoladi.
HTTP / REST Client 
# Foydalanuvchini olish (Frontend fetch)
fetch('https://api.w3learn.uz/users/42', {
  method: 'GET',
  headers: { 'Accept': 'application/json' }
})
.then(res => res.json())
.then(data => console.log(data));
🌐 REST API HTTP Response:
💡 Hech qachon GET metodi orqali parollarni uzatmang, chunki URL manzil server loglarida va brauzer tarixida ochiq saqlanib qoladi.

Metodlar REST API Mavzu #6

POST Metodi: Yangi Resurs Yaratish

Serverda yangi ma'lumot yoki resurs hosil qilish uchun ishlatiladi. So'rov ma'lumotlari so'rov tanasida (Request Body) JSON formatida yuboriladi.

  • Idempotent emas: Bir xil POST so'rovini 3 marta yuborsangiz, bazada 3 ta alohida yangi yozuv yaratiladi.
  • Muvaffaqiyatli yaratilganda server odatda 201 Created status kodi va yangi yaratilgan resursni qaytaradi.
HTTP / REST Client 
# Yangi kurs qo'shish so'rovi
fetch('https://api.w3learn.uz/courses', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({
    title: "Docker Asoslari",
    durationHours: 12
  })
})
.then(res => res.json())
.then(data => console.log(data));
🌐 REST API HTTP Response:
💡 Server 201 Created qaytarganda, sarlavhalarda (Location header) yangi resursning URL manzilini ko'rsatish yaxshi amaliyotdir.

Metodlar REST API Mavzu #7

PUT Metodi: Resursni To'liq Almashtirish

Mavjud resursni boshidan oxirigacha yangilash (to'liq almashtirish) uchun xizmat qiladi.

  • Idempotent: PUT so'rovini bir necha bor qaytarsangiz ham resurs bir xil holatda qoladi.
  • Agar siz obyektning faqat bitta maydonini yuborsangiz, qolgan barcha ko'rsatilmagan maydonlar o'chib ketishi yoki null ga aylanishi mumkin.
HTTP / REST Client 
# Foydalanuvchi profilini to'liq almashtirish
fetch('https://api.w3learn.uz/users/42', {
  method: 'PUT',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    name: "Sherzod Aliyev",
    role: "Senior Developer",
    age: 26
  })
});
🌐 REST API HTTP Response:
💡 Butun resursni emas, faqat bitta maydonni yangilash kerak bo'lsa, PUT o'rniga PATCH ishlatiladi.

Metodlar REST API Mavzu #8

PATCH Metodi: Qisman Yangilash

Mavjud resursning faqat ma'lum bir maydonini yoki bir nechta qismlarini o'zgartirish (Partial Update).

  • Tarmoq trafigini tejaydi: Butun og'ir obyektni yuborish shart emas, faqat o'zgargan maydon jo'natiladi.
  • Masalan, foydalanuvchining faqat familiyasi yoki faollik statusini o'zgartirish.
HTTP / REST Client 
# Faqat statusni o'zgartirish
fetch('https://api.w3learn.uz/users/42', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    status: "suspended"
  })
});
🌐 REST API HTTP Response:
💡 Zamonaviy frontend ilovalarda profillarni yoki tovar qoldig'ini yangilashda eng ko'p PATCH qo'llaniladi.

Metodlar REST API Mavzu #9

DELETE Metodi: Resursni O'chirish

Ko'rsatilgan ID ga ega resursni serverdan yoki ma'lumotlar bazasidan o'chirish.

  • Idempotent: Resurs o'chirilgach, qayta DELETE so'rovi yuborilsa server xuddi shunday o'chirilganini bildiradi (yoki 404 qaytaradi).
  • Odatda javob tanasi bo'lmaydi va 204 No Content status kodi qaytadi.
HTTP / REST Client 
# Foydalanuvchini o'chirish
fetch('https://api.w3learn.uz/users/42', {
  method: 'DELETE'
});
🌐 REST API HTTP Response:
💡 Haqiqiy loyihalarda odatda jismoniy o'chirish (Hard Delete) o'rniga Soft Delete (is_deleted = true) qilinadi.

Statuslar REST API Mavzu #10

2xx Muvaffaqiyat Kodlari (200, 201, 204)

Mijozning so'rovi server tomonidan muvaffaqiyatli qabul qilingan va bajarilganini bildiruvchi kodlar oilasi.

  • 200 OK: Standart muvaffaqiyatli javob (GET, PUT, PATCH uchun).
  • 201 Created: Yangi resurs muvaffaqiyatli yaratildi (POST uchun).
  • 204 No Content: Amal muvaffaqiyatli bajarildi, lekin qaytarish uchun javob tanasi (body) yo'q (DELETE uchun).
HTTP / REST Client 
# Turli muvaffaqiyatli so'rovlar javoblari
GET    /users      -> 200 OK (foydalanuvchilar massivi)
POST   /users      -> 201 Created (yangi user)
DELETE /users/5    -> 204 No Content (bo'sh)
🌐 REST API HTTP Response:
💡 Har bir amal uchun to'g'ri status kodini qaytarish REST API madaniyatining eng muhim qismidir.

Statuslar REST API Mavzu #11

3xx Yo'naltirish Kodlari (Redirection)

So'ralgan resurs boshqa manzilga ko'chirilganini va mijoz o'sha yangi manzilga o'tishi kerakligini bildiruvchi kodlar.

  • 301 Moved Permanently: Resurs butunlay boshqa yangi URL ga ko'chgan (qidiruv botlari va brauzerlar xotirasida yangi URL saqlanadi).
  • 302 Found: Vaqtinchalik yo'naltirish.
  • 304 Not Modified: Resurs mijoz so'nggi marta olganidan beri o'zgarmagan; ma'lumotni keshdan olavering (trafik tejaladi).
HTTP / REST Client 
# HTTP dan HTTPS ga yo'naltirish
HTTP/1.1 301 Moved Permanently
Location: https://w3learn.uz/api/v1/courses
🌐 REST API HTTP Response:
💡 304 Not Modified kesh mexanizmlari (ETag, If-Modified-Since) bilan birga ishlab server yuklamasini keskin kamaytiradi.

Xatoliklar REST API Mavzu #12

4xx Mijoz Xatoliklari (Client Errors)

So'rovda mijoz (Frontend) tomonidan xatolikka yo'l qo'yilganligini ko'rsatuvchi kodlar.

  • 400 Bad Request: Yuborilgan ma'lumotlar noto'g'ri (validatsiya xatosi, masalan email noto'g'ri formatda yoki majburiy maydon qolib ketgan).
  • 401 Unauthorized: Foydalanuvchi tizimga kirmagan (token yo'q yoki muddati o'tgan).
  • 403 Forbidden: Foydalanuvchi tizimga kirgan, lekin bu amalni bajarishga huquqi (ruxsati) yetarli emas (masalan oddiy talaba admin panelga kirmoqchi).
  • 404 Not Found: So'ralgan URL yoki ID dagi resurs topilmadi.
  • 429 Too Many Requests: Belgilangan vaqt ichida haddan tashqari ko'p so'rov yuborildi (Rate Limiting).
HTTP / REST Client 
# Validatsiya xatosi namunasi (HTTP 400)
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": [
    "email must be an email",
    "password must be longer than 8 characters"
  ]
}
🌐 REST API HTTP Response:
💡 401 bilan 403 ning farqi: 401 — 'Siz kimsiz, tanimayapman', 403 — 'Sizni taniyman, lekin bu yerga kirishingizga ruxsat yo'q'.

Xatoliklar REST API Mavzu #13

5xx Server Xatoliklari (Server Errors)

Mijozning so'rovi to'g'ri bo'lsa-da, serverning ichki xatoligi tufayli so'rov bajarilmay qolgan holatlar.

  • 500 Internal Server Error: Backend kodida kutilmagan istisno (Unhandled Exception) yuz berdi (dasturchining xatosi).
  • 502 Bad Gateway: Nginx kabi proksi-server orqadagi Node.js/Python serverdan yaroqli javob ololmadi (backend yiqilgan yoki o'chgan).
  • 503 Service Unavailable: Server haddan tashqari yuklangan yoki profilaktika (texnik ishlar) sababli vaqtincha ishlamayapti.
  • 504 Gateway Timeout: Orqa fondagi server javob berishga ulgurmadi (so'rov vaqti tugadi).
HTTP / REST Client 
# Server xatoligi namunasi (HTTP 500)
{
  "statusCode": 500,
  "error": "Internal Server Error",
  "message": "Database connection timeout at line 45 in db.js"
}
🌐 REST API HTTP Response:
💡 Production muhitda hech qachon 500 xatosida ichki ma'lumotlar bazasi parollari yoki kod strukturasini (Stack Trace) mijozga ko'rsatmang!

Sarlavhalar REST API Mavzu #14

HTTP Sarlavhalari (Request va Response Headers)

Sarlavhalar (Headers) — so'rov va javob haqidagi meta-ma'lumotlarni (ma'lumot formati, shifrlash, til, xavfsizlik) uzatuvchi kalit-qiymat juftliklaridir.

  • Authorization: Bearer — foydalanuvchi shaxsini tasdiqlovchi token.
  • User-Agent: — so'rov qaysi brauzer yoki ilovadan yuborilayotgani.
  • Cache-Control: no-cache, max-age=3600 — kesh qoidalari.
  • Set-Cookie: — server mijoz brauzeriga cookie saqlashni buyuradi.
HTTP / REST Client 
# To'liq so'rov sarlavhalari namunasi:
POST /api/v1/orders HTTP/1.1
Host: api.w3learn.uz
Authorization: Bearer eyJhbGciOiJIUzI1Ni...
Content-Type: application/json
Accept-Language: uz-UZ,uz;q=0.9
User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X)
🌐 REST API HTTP Response:
💡 Maxsus loyiha sarlavhalari odatda `X-` prefiksi bilan boshlanadi (masalan `X-Request-ID`).

Format REST API Mavzu #15

Content-Type va Accept: Format Kelishuvi

Mijoz va server o'rtasida ma'lumot qaysi formatda uzatilayotganini aniqlashtirish (Content Negotiation).

  • Content-Type: 'Men sizga qanday formatdagi ma'lumot yuboryapman' (so'rov tanasining formati). REST da deyarli doim application/json.
  • Accept: 'Menga qanday formatda javob qaytarishingizni xohlayman' (masalan: Accept: application/json yoki image/webp).
  • Fayl yuklashda: multipart/form-data.
HTTP / REST Client 
// Axios orqali sarlavhalarni sozlash
axios.post('/api/upload', formData, {
  headers: {
    'Content-Type': 'multipart/form-data',
    'Accept': 'application/json'
  }
});
🌐 REST API HTTP Response:
💡 Agar Content-Type: application/json ko'rsatmasangiz, ko'plab backend freymvorklari req.body ni tahlil qila olmay bo'sh qoldiradi.

Xavfsizlik REST API Mavzu #16

CORS va Preflight (OPTIONS): Xavfsizlik Qoidasi

CORS (Cross-Origin Resource Sharing) — bitta domenda (masalan frontend.uz) joylashgan veb-ilova boshqa domendagi (masalan api.baza.uz) API ga murojaat qilganda brauzer tomonidan tekshiriladigan xavfsizlik mexanizmidir.

  • Brauzerlar xakerlik hujumlarining oldini olish uchun boshqa domenga ruxsatsiz AJAX so'rov yuborishni bloklaydi.
  • Server maxsus sarlavhalar orqali ruxsat berishi kerak: Access-Control-Allow-Origin: * yoki https://frontend.uz.
  • Preflight (OPTIONS): Murakkab so'rovlardan oldin brauzer avval avtomatik OPTIONS so'rovi yuborib serverning ruxsatini tekshirib oladi.
HTTP / REST Client 
// Node.js Express da CORS ni to'g'ri sozlash
const cors = require('cors');

app.use(cors({
  origin: ['https://w3learn.uz', 'https://admin.w3learn.uz'],
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  credentials: true
}));
🌐 REST API HTTP Response:
💡 'CORS Error' — backend ning xatosi emas, balki serverda to'g'ri CORS sarlavhalari sozlanmaganligi sababli brauzer tomonidan so'rovning to'xtatilishidir.

Xavfsizlik REST API Mavzu #17

Basic Auth va API Kalitlari (API Keys)

API larni himoyalashning eng sodda va klassik usullari.

  • Basic Authentication: Login va parol ikkitalik nuqta bilan birlashtirilib, Base64 formatida shifrlanadi (Authorization: Basic YWRtaW46c2lybGlwYXJvbA==).
  • API Key: Tashqi servislarga (masalan ob-havo, SMS-shlyuz, xaritalar) murojaat qilish uchun beriladigan maxsus uzun sirli satr (masalan: x-api-key: 9a8b7c6d...).
HTTP / REST Client 
# API kalit bilan so'rov yuborish
curl -H "X-API-KEY: w3_live_89f4b7a1e0" https://api.weather.com/v1/tashkent
🌐 REST API HTTP Response:
💡 Basic Auth da Base64 shunchaki o'qilishi qiyinlashtirilgan matn (encoding) xolos, shifrlash (encryption) emas; shu sababli faqat HTTPS orqali uzatilishi shart!

Autentifikatsiya REST API Mavzu #18

Bearer Token va Authorization Header

Zamonaviy REST API larda eng ko'p qo'llaniladigan autentifikatsiya uslubi. 'Bearer' so'zi 'ushbu tokenga ega bo'lgan kishi' ma'nosini anglatadi.

  • Mijoz login qilganda server unga token (odatda JWT) beradi.
  • Keyingi barcha so'rovlarda mijoz ushbu tokenni sarlavhada yuboradi: Authorization: Bearer .
  • Server har safar parolni tekshirmaydi, faqat tokenni tasdiqlaydi.
HTTP / REST Client 
// Bearer token bilan himoyalangan API ga murojaat
const token = localStorage.getItem('accessToken');

fetch('https://api.w3learn.uz/profile', {
  headers: {
    'Authorization': `Bearer ${token}`,
    'Content-Type': 'application/json'
  }
});
🌐 REST API HTTP Response:
💡 Agar token xato bo'lsa yoki muddati tugasa, server darhol 401 Unauthorized qaytaradi.

Xavfsizlik REST API Mavzu #19

JWT (JSON Web Token): Tuzilishi va Tekshirish

JWT — ikki tomon o'rtasida ma'lumotlarni xavfsiz va ixcham JSON ko'rinishida uzatish uchun ochiq sanoat standarti (RFC 7519).

  • JWT nuqtalar bilan ajratilgan 3 qismdan iborat: Header.Payload.Signature.
  • Header (Qizil): Algoritm turi (masalan HS256 yoki RS256).
  • Payload (Binafsha): Foydalanuvchi ma'lumotlari (id, ism, rol, amal qilish muddati - exp).
  • Signature (Ko'k): Maxfiy kalit (Secret Key) bilan tasdiqlangan imzo. U token ichidagi ma'lumotlar o'zgartirilmaganligini kafolatlaydi.
HTTP / REST Client 
// Node.js da jsonwebtoken kutubxonasi bilan ishlash
const jwt = require('jsonwebtoken');
const SECRET_KEY = "w3learn_maxfiy_kalit";

// 1. Token yasash (Sign)
const token = jwt.sign(
  { userId: 101, role: 'admin' },
  SECRET_KEY,
  { expiresIn: '2h' }
);
console.log("Hosil bo'lgan JWT:", token);

// 2. Tokenni tekshirish (Verify)
const decoded = jwt.verify(token, SECRET_KEY);
console.log("Token ichidagi ma'lumot:", decoded);
🌐 REST API HTTP Response:
💡 Server JWT ni bazadan qidirmasdan ham matematik imzo orqali o'zida bir zumda tekshira oladi; bu esa server yuklamasini keskin yengillatadi.

Avtorizatsiya REST API Mavzu #20

OAuth 2.0: 'Google orqali Kirish' Mexanizmi

OAuth 2.0 — foydalanuvchining parolini uchinchi tomon dasturiga bermasdan, uning hisobidagi ma'lumotlarga xavfsiz cheklangan ruxsat (delegated authorization) berish protokoli.

  • Saytga 'Google orqali kirish' yoki 'GitHub orqali kirish' tugmalari aynan OAuth 2.0 asosida ishlaydi.
  • Rollari: Resource Owner (foydalanuvchi), Client (bizning sayt), Authorization Server (Google), Resource Server (Google API).
  • Mijoz ilovasi parolni hech qachon ko'rmaydi, faqat vaqtinchalik Access Token oladi.
HTTP / REST Client 
# OAuth 2.0 Oqimi (Authorization Code Flow)
1. Foydalanuvchi 'Google orqali kirish' tugmasini bosadi.
2. Sayt foydalanuvchini Google ning login sahifasiga yo'naltiradi.
3. Foydalanuvchi ruxsat beradi (Consent Screen).
4. Google bizning saytimizga maxsus vaqtinchalik 'code' bilan qaytaradi.
5. Bizning backend serverimiz ushbu 'code' ni Google serveriga yuborib 'Access Token' ga almashtiradi.
6. Token orqali foydalanuvchining ismi va emailini olib saytga kiritamiz.
🌐 REST API HTTP Response:
💡 OAuth 2.0 avtorizatsiya uchun, uning ustiga qurilgan OpenID Connect (OIDC) esa autentifikatsiya (shaxsni aniqlash) uchun xizmat qiladi.

Arxitektura REST API Mavzu #21

API Versiyalash Strategiyalari (/v1, Headers)

Vaqt o'tishi bilan API o'zgaradi va kengayadi. Eski mobil ilovalar va mijozlar to'satdan buzilib qolmasligi uchun (Backward Compatibility) API larni versiyalash shart.

  • 1. URI Versioning (Eng mashhur va qulay): https://api.site.uz/v1/users va https://api.site.uz/v2/users.
  • 2. Header Versioning: Accept: application/vnd.company.v2+json yoki X-API-Version: 2.
  • 3. Query Param: /api/users?version=2.
HTTP / REST Client 
// Express da versiyalangan marshrutlar
const v1Router = require('./routes/v1');
const v2Router = require('./routes/v2');

app.use('/api/v1', v1Router);
app.use('/api/v2', v2Router);

💡 Har doim yangi loyihani boshlagan kuniyoq URL ga `/v1/` prefiksini qo'yishni unutmang.

Optimizatsiya REST API Mavzu #22

Paginatsiya: Katta Ma'lumotlarni Bo'lib Uzatish

Agar ma'lumotlar bazasida 1,000,000 ta mahsulot bo'lsa, ularning barchasini bitta so'rovda qaytarish serverni qulatadi. Buning o'rniga ma'lumotlar sahifalarga bo'linadi (Pagination).

  • Offset-based: /api/v1/products?page=2&limit=20 (2-sahifa, har sahifada 20 tadan). Oddiy, ammo katta ma'lumotlarda sekinlashishi mumkin.
  • Cursor-based (Kesh/Lenta uchun eng zo'ri): /api/v1/posts?cursor=eyJpZCI6MTB9&limit=10 (Instagram yoki Twitter kabi cheksiz skroll uchun). Tezlik doimo O(1).
HTTP / REST Client 
# Paginatsiyalangan API javobining ideal namunasi:
GET /api/v1/products?page=1&limit=2
🌐 REST API HTTP Response:
💡 Har doim javobda `meta` (umumiy sahifalar va elementlar soni) ma'lumotlarini qaytarish frontend dasturchilarning ishini osonlashtiradi.

Dizayn REST API Mavzu #23

Filtrlash, Saralash va Qidiruv (Query Params)

Foydalanuvchilarga faqat kerakli ma'lumotlarni saralab olish imkonini beruvchi URL parametrlari.

  • Filtrlash: /products?category=laptops&in_stock=true.
  • Saralash (Sorting): /products?sort=price_desc (yoki sort=-price).
  • Qidiruv (Search): /products?search=apple.
  • Maydonlarni tanlash (Field selection): /products?fields=id,title,price (tarmoq trafigini tejash uchun).
HTTP / REST Client 
// Node.js Express da parametrlarni qabul qilish
app.get('/api/v1/products', async (req, res) => {
  const { category, min_price, sort, page = 1, limit = 20 } = req.query;
  
  // Baza so'roviga filtrlarni qo'llaymiz
  const products = await Product.find({
    ...(category && { category }),
    ...(min_price && { price: { $gte: Number(min_price) } })
  })
  .sort(sort === 'price_desc' ? { price: -1 } : { price: 1 })
  .skip((page - 1) * limit)
  .limit(Number(limit));

  res.json({ success: true, data: products });
});
🌐 REST API HTTP Response:
💡 Query parametrlari URL ning `?` belgisidan keyin yoziladi va o'zaro `&` bilan bog'lanadi.

Hujjatlash REST API Mavzu #24

Swagger va OpenAPI: Interaktiv Hujjatlar

OpenAPI (ilgari Swagger) — REST API larni hujjatlashtirishning global standarti. U brauzerda barcha marshrutlar, parametrlar va JSON namunalarini ko'rish hamda to'g'ridan-to'g'ri sinab ko'rish ('Try it out') imkonini beradi.

  • Frontend va Mobil dasturchilar backend kodiga qaramasdan qanday so'rov yuborishni aniq ko'rib turishadi.
  • Ko'plab tillarda (FastAPI, NestJS, Spring Boot) kod yozilganda Swagger hujjati avtomatik ravishda hosil qilinadi.
  • Standart manzil: https://api.w3learn.uz/api-docs.

Xavfsizlik REST API Mavzu #25

RESTful API Eng Yaxshi Amaliyotlari va Xavfsizlik

Production darajasidagi professional REST API arxitekturasining oltin qoidalari.

  • 1. Doimo HTTPS ishlating: Hech qachon ochiq HTTP orqali ma'lumot almashmang.
  • 2. Rate Limiting joriy qiling: DDoS va parollarni taxmin qilish hujumlariga qarshi har bir IP uchun minutiga maksimal so'rovlar chegarasini belgilang.
  • 3. Barcha kiruvchi ma'lumotlarni tekshiring (Input Validation): SQL Injection va XSS hujumlaridan himoyalanish uchun Zod, Joi yoki class-validator ishlating.
  • 4. To'g'ri HTTP status kodlaridan foydalaning: Hech qachon xatolik bo'lganda 200 OK ichida { error: true } qaytarmang!
  • 5. Xavfsizlik sarlavhalari: Helmet orqali himoya sarlavhalarini yoqing.
HTTP / REST Client 
# Xavfsizlik bo'yicha to'liq tekshiruv:
[✓] HTTPS Shifrlash yoqilgan
[✓] CORS faqat ishonchli domenlarga ruxsat beradi
[✓] Rate Limiting (1 daqiqada max 100 so'rov)

[✓] Barcha JSON tana ma'lumotlari qat'iy sanitizatsiya qilinadi
[✓] Swagger hujjati dolzarb holatda
